# บทสรุปผู้บริหาร — SentinelAI

**SentinelAI** คือผู้ช่วยวิเคราะห์เหตุการณ์ด้านความปลอดภัย (SOC Triage Copilot) ที่ใช้โมเดลภาษา `gemma-4-E4B-it`
ผ่าน proxy ของรายวิชา เพื่อช่วยนักวิเคราะห์ SOC ระดับเริ่มต้นคัดกรองแจ้งเตือนความปลอดภัย ข้อมูลทั้งหมดเป็นข้อมูลสังเคราะห์
ขององค์กรสมมติ และระบบเป็นเพียงผู้ช่วย ไม่ได้ดำเนินการตอบสนองเหตุการณ์เองโดยอัตโนมัติ

**การทำงานหลัก**
1. สกัดข้อมูลจากแจ้งเตือนเป็นโครงสร้างที่ตรวจสอบด้วย Pydantic และตัดค่าที่ไม่ปรากฏในข้อความจริงทิ้ง (ป้องกันการแต่งข้อมูล)
2. Agent เลือกใช้เครื่องมือที่อนุญาตเท่านั้น (ค้นหา playbook, คำนวณความรุนแรง, ค้นประวัติเหตุการณ์) ภายใต้ขีดจำกัดจำนวนขั้นและเวลา
3. คำนวณระดับความรุนแรงด้วยตารางคะแนนแบบกำหนดแน่นอน (PB-002) ซึ่งโมเดลไม่สามารถแก้ไขได้
4. สร้างรายงานพร้อมอ้างอิงเอกสารที่ถูกค้นคืนจริง หากอ้างอิงไม่ถูกต้องระบบจะให้แก้ไข และหากยังผิดจะคืนข้อผิดพลาดแทนการสร้างรายงานปลอม

**ผลการประเมินที่วัดจริง** (ชุดทดสอบที่แยกไว้ 16 คำถาม, ตอบได้ 14 ข้อ)
- Baseline BM25 แบบ chunk คงที่: Recall@3 = 0.679, MRR@5 = 0.696
- ค่าที่เลือกจากชุด dev (Hybrid BM25 + MiniLM, α = 0.3, chunk ตามหัวข้อ): Recall@3 = 0.750, MRR@5 = 0.729
- ดีขึ้นเล็กน้อย (ชนะ 2 แพ้ 1 เสมอ 11 คำถาม) แต่ชุดข้อมูลมีขนาดเล็ก จึงยังไม่สามารถสรุปเชิงสถิติได้

**การประเมินแบบ end-to-end กับ Gemma จริง** (`gemma-4-E4B-it`, temperature 0)
- รอบแรก (r0) ความแม่นยำของระดับความรุนแรงบนชุดทดสอบอยู่ที่ 0.571 เพราะโมเดลให้ alert confidence เป็น "medium" เกือบทุกเคส
- ปรับปรุง 3 รอบ ทุกรอบเขียนชุด holdout ใหม่ 16 เคสก่อนแก้ เพื่อวัดผลกับข้อมูลที่ระบบไม่เคยเห็น
- ผลบนชุดที่ไม่เคยเห็น (severity): r1 0.462 → 0.615, r2 0.923 → 0.923, r3 0.615 → 0.846
- ผลบนชุดที่ไม่เคยเห็น (อ้างอิง playbook ที่เกี่ยวข้อง): r2 0.812 → 0.938
- เวอร์ชันสุดท้าย (r3) บนชุดทดสอบเดิม: output ถูก schema, ประเภทเหตุการณ์, ความรุนแรง และการอ้างอิง = 1.000 ทั้งหมด
  แต่ชุดนี้เคยถูกดูเคสที่ผิดมาก่อนแก้ จึงไม่ใช่ตัวเลขแบบ blind
- รายละเอียดทุกรอบอยู่ใน docs/EXPERIMENT_LOG.md

**ข้อจำกัด**: ข้อมูลสังเคราะห์ขนาดเล็ก, ชุดทดสอบเล็ก, การตรวจจับ prompt injection เป็นแบบ pattern,
ไม่มีระบบยืนยันตัวตน จึงควรรันในเครื่องเท่านั้น
