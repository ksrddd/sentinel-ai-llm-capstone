# End-to-end Improvement Log

This log records each change to the LLM pipeline after the first end-to-end evaluation, why it was made,
which data informed it, and what it did to the metrics. All numbers come from
`eval/results/rounds/<round>/e2e_summary*.json` (written by `python -m eval.run_e2e_eval --round <round>`)
and the table below is regenerated by `python -m eval.compare_rounds`. Model: `gemma-4-E4B-it`, temperature 0,
through the class proxy. Retrieval configuration is unchanged in every round (`hybrid-sbert-section-a0.3`).

## Evaluation discipline

* **dev v1** (13 cases) is the development set: changes are designed from its failures.
* **test v1** (12 cases) was used for the first report. Its failures were inspected after round 0, so from
  round 1 on it is a *seen* set and its numbers are no longer an unbiased estimate.
* **holdout v2** (`eval/datasets/e2e_holdout_v2.jsonl`, 16 cases) was written and labelled before round 1 ran
  on it. Its failures were inspected after round 1, so it is *seen* from round 2 on.
* **holdout v3** (`eval/datasets/e2e_holdout_v3.jsonl`, 16 cases) was written and labelled before round 2
  ran on it; its per-case results for round 1 were not inspected before round 2 was designed. It is *seen*
  from round 3 on.
* **holdout v4** (`eval/datasets/e2e_holdout_v4.jsonl`, 16 cases) was written and labelled before round 3
  was designed; only its aggregate round 2 numbers were looked at.
* Each new round therefore gets one data set it has never been tuned on. Labels in every set follow the
  PB-002 formula and are checked by `tests/test_eval_dataset.py`.
* Sets are small (12-16 cases, 5-13 with a severity label): one case moves severity accuracy by 6-20
  points. Differences of one or two cases should not be read as real effects.

## Rounds

### r0_baseline
Original prompts. Model chose `alert_confidence` itself with only the words low/medium/high.

Observed failures (test v1, dev v1): Gemma rated almost every alert `medium` confidence, lowered confidence
when malware was quarantined (that should lower impact instead), and under-rated impact when execution was
confirmed. Insufficient-evidence alerts did not cite PB-014 because the agent searched the vague alert text.

### r1_factor_rubric
Designed from dev v1 failures.
* Extraction prompt gets explicit definitions of alert confidence and observed impact
  (`FACTOR_RUBRIC` in `app/llm/prompts.py`).
* When the extracted type is `undetermined`, the orchestrator also searches for the insufficient-evidence
  procedure (`INSUFFICIENT_EVIDENCE_QUERY` in `app/services/analysis.py`).

### r2_evidence_kind_fallback
Designed from failures seen in test v1 and holdout v2 under r1 (blind check: holdout v3).
* The model no longer rates confidence directly. It classifies the evidence as `specific_telemetry`,
  `anomaly` or `vague`, and confidence is mapped deterministically (high / medium / low) in
  `ExtractedIncident` (`app/schemas/alert.py`). Under r1 the model still hedged to `medium` on specific
  telemetry (Q16, H06, H10).
* Impact definition gives concrete examples of confirmed execution (process still alive, command output
  returned, settings changed, accounts created).
* If every agent search abstained (terse keyword queries such as "malware quarantine invoice_viewer.exe"
  scored under the threshold), the orchestrator repeats the search with the incident label plus the alert
  evidence. Previously this fallback ran only when the agent never searched (Q08, H03, H04 cited nothing).

### r2b_repeat_noise_check
Not a change: round 2 run a second time on holdout v3 to measure run-to-run variation at temperature 0.
Incident type, severity and severity factors were identical for all 16 cases. Only the optional extra
citations in the drafted report differed (3 cases added a second or third document; the relevant document
was cited in both runs). Severity and type differences between rounds are therefore caused by the changes,
not by sampling noise; citation-count details can vary.

### r3_outcome_flag_label_fallback
Designed from failures seen in test v1, holdout v2 and holdout v3 under r2 (blind check: holdout v4).
* Impact under-rating persisted when execution was shown (H04 miner "running for two hours", H06 command
  output returned). The model now also answers a yes/no question, `malicious_outcome_confirmed`; when true it
  raises impact to `confirmed_limited` (it can never lower impact).
* `vague` was chosen for alerts with a hostname and exact volumes (Q16, H08). The definition now says an
  alert that names a host and any concrete count, volume, command, file, process or address is not vague.
* V02 still cited nothing: both the agent's query and the label + evidence query abstained. A last fallback
  searches the incident label alone; a check of every label showed its own playbook ranked first and above
  the threshold.

## Reading the results

* **Blind checks only.** r1 on holdout v2 (severity 0.462 to 0.615), r2 on holdout v3 (severity unchanged
  at 0.923, relevant citation 0.812 to 0.938) and r3 on holdout v4 (severity 0.615 to 0.846, relevant
  citation stays 1.000) are the only comparisons on data the change was not designed from.
* **r3 is not better everywhere.** On holdout v3 (seen) it lost one severity case (V16 impact went back to
  `suspected`) and one citation (V02 cited PB-010 instead of PB-007). Pooled over all five sets, correct
  severities went from 40/51 (r2) to 43/51 (r3). LLM prompt changes are not monotonic: a wording change
  aimed at one factor can move other cases.
* r3 is the configuration in the code and in `eval/results/e2e_summary.json` (test v1).

## Remaining issues (after r3)

* Impact on confirmed execution is still sometimes `suspected` (H04, H06, V16): the outcome flag does not
  fire on every case.
* Evidence classification is unstable on short natural-language alerts: W11 (credentials submitted) and
  V11 were classed `vague`, H07/W10 `anomaly` where the label says specific telemetry. Several of these are
  borderline between anomaly and specific telemetry, so part of the error is label ambiguity.
* Type confusions on deliberately ambiguous cases (Q03 brute force vs suspicious login, Q07/Q17/W08
  classified `undetermined`). These are safe failures because undetermined cases always go to human review.
* Every set is small; one case is 6-20 points of accuracy. A further round would need a new unseen holdout
  set (v5) to be measured honestly.
